## Часть 2. Три ключевые находки

### Находка 1: Отсутствие авторизации на роуте списка бронирований `GET /events/:id/bookings` (Утечка PII)
- **Что не так:** Публичный эндпоинт `GET /events/:id/bookings` доступен без проверки JWT-токена пользователя или админа. Любой анонимный пользователь может запросить список всех бронирований конкретного мероприятия и получить персональные данные гостей (имена, e-mail адреса).
- **Чем грозит:** Нарушение требований по защите персональных данных (GDPR / 152-ФЗ). Конкуренты или злоумышленники могут собрать базу клиентов и e-mail участников всех мероприятий.
- **Как воспроизвести:**
  1. Выполнить HTTP-запрос `GET https://project-alfa-backend-pevqwdw4la-uc.a.run.app/events/<EVENT_ID>/bookings` без передачи заголовка `Authorization`.
  2. В ответе приходит HTTP 200 OK с полным списком броней и PII клиентов.

---

### Находка 2: Наличие тестового/отладочного эндпоинта `GET /auth/debug/token-info` на боевом бэкенде
- **Что не так:** Роут `GET /auth/debug/token-info` предназначен для отладки информации о токене. Проверка среды `if (process.env.NODE_ENV === 'production')` опирается исключительно на переменную окружения, но при отсутствии этой переменной или неверной настройке Cloud Run эндпоинт остается активным на боевом стенде.
- **Чем грозит:** Утечка внутренней структуры токена и служебных метаданных авторизации в продакшене.
- **Как воспроизвести:**
  1. Авторизоваться обычным пользователем.
  2. Отправить `GET https://project-alfa-backend-pevqwdw4la-uc.a.run.app/auth/debug/token-info` с заголовком `Authorization: Bearer <USER_TOKEN>`.

---

### Находка 3: Использование метода POST для обновления профиля `POST /auth/profile` вместо PUT / PATCH
- **Что не так:** Роут обновления данных профиля пользователя объявлен с использованием декоратора `@Post('profile')` вместо семантически корректных REST-методов `PUT` или `PATCH`.
- **Чем грозит:** Путаница на фронтенде и при интеграции API, некорректная обработка запросов прокси-серверами и кэширующими слоями (POST по стандарту считаются неидемпотентными).
- **Как воспроизвести:**
  1. Выполнить `POST /auth/profile` с новым никнеймом в теле запроса. Запрос успешный, но нарушает стандарты REST API.

---

### Находка 4: Отсутствие авторизации и подтверждения email при бронировании `POST /events/:id/book` (Риск исчерпания мест / DOS)
- **Что не так:** Эндпоинт `POST /events/:id/book` доступен абсолютно анонимно без авторизации (`JwtAuthGuard`), без верификации email (без ввода кода / ссылки из письма) и без защиты от ботов (капча / rate limiter). При этом система сразу создает бронь и списывает количество доступных мест на мероприятии.
- **Сценарий злоупотребления:**
  1. Атакующий или конкурент пишет простой скрипт-бот, который генерирует случайные имена и e-mail адреса (`bot1@temp.com`, `bot2@temp.com`...).
  2. За секунды скрипт отправляет серию запросов на `POST /events/<EVENT_ID>/book` с указанием максимального доступного количества участников.
  3. Все места на ивент моментально забиваются фейковыми бронированиями (Denial of Service для реальных участников). Организатор теряет клиентуру, а реальные пользователи видят статус «Мест нет».
- **Чем закрывать:**
  1. **Обязательная авторизация:** Повесить `@UseGuards(JwtAuthGuard)`, чтобы бронировать места могли только зарегистрированные пользователи.
  2. **Подтверждение email (Double Opt-In):** Сохранять бронь в статусе `PENDING` и финализировать только после перехода по ссылке из e-mail или ввода 6-значного кода.
  3. **Rate Limiting и защита от ботов:** Добавить `@nestjs/throttler` на эндпоинт бронирования и проверку reCAPTCHA/Turnstile на фронтенде.

## Часть 3. Вердикт: Что чинить первым и почему

1. **Первоочередная задача (Приоритет 1): Защитить роут `GET /events/:id/bookings`**
   - **Почему:** Это прямая уязвимость утечки персональных данных пользователей (PII). Роут должен быть защищен `AdminJwtAuthGuard` (или перенесен исключительно под префикс `/admin/events/:id/bookings`, который уже защищен).

2. **Вторая задача (Приоритет 2): Отключить / Убрать `GET /auth/debug/token-info` из продакшн сборки**
   - **Почему:** Отладочные роуты не должны попадать в продакшн-код API.

3. **Третья задача (Приоритет 3): Исправить метод `POST /auth/profile` на `PATCH /auth/profile`**
   - **Почему:** Приведение API к единым REST-стандартам повышает надежность интеграции фронтенда и предотвращает баги при обработке сетевых запросов.

4. **Четвертая задача (Приоритет 4): Защитить роут бронирования `POST /events/:id/book`**
   - **Почему:** Отсутствие ограничений позволяет полностью заблокировать доступность всех мероприятий на платформе за считанные секунды с помощью анонимных ботов.
